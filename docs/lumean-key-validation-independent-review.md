## Статические результаты

1. **Отклонённая замена не записывает настройки.** Store проверяет непустой результат существующего `trim()` до шифрования нового ключа, обработки proxy и единственного `write(next)`. При ошибке остаётся прежний файл целиком, включая ключ, Base URL и proxy. Пустой ввод по-прежнему сохраняет старый ключ; новых действий очистки нет.
2. **Нет придуманного формата ключа.** Общий предикат отклоняет C0 кроме TAB, DEL и кодовые единицы выше U+00FF, включая суррогаты. Внутренние пробелы, TAB и диапазон 0x80–0xFF он пропускает. Ограничений длины, префикса или набора букв/цифр не добавлено; нормализация по краям осталась прежней.
3. **Старый непередаваемый ключ останавливает запрос локально.** `requireApiKey()` вызывается из `requestOnce()` до proxy/fetch и вне сетевого catch. Возникает `VoicerClientError` с `code: configuration`, `retryable: false`, `creationUncertain: false`; цикл request не повторяет её как network failure. Это распространяется на Check и загрузку шаблонов. Сообщение фиксированное, без значения ключа, фрагмента, позиции, кода символа, отпечатка или cause с секретом. Новые события диагностики не добавлены.
4. **Новый платный запрос не получает ложный pending из-за уже некорректного ключа.** Первый preflight выполнен до `onBeforeOrderCreate`. После создания отметки `requestOnce()` заново читает и проверяет ключ. Если между этими этапами ключ удалён или стал непередаваемым, определённый локальный отказ до транспорта идёт в существующий `onOrderRejected`; снимается отметка этой неотправленной попытки. Исключение самого `onBeforeOrderCreate` находится вне этого catch и не вызывает снятие старой отметки.
5. **Старые uncertain/known-order защиты сохранены.** Scheduler блокирует pending без ID до запуска клиента, а `updateSubmission` отказывает при уже имеющемся checkpoint/receipt. При `resumeOrderId` ветка нового POST и новый preflight перед ним пропускаются; ошибка последующего чтения заказа оборачивается существующим `afterKnownOrderError` с `orderKnown: true` и запретом автоматического повторного заказа. Новый код не очищает сохранённый ID и не объявляет прежний неопределённый запрос неотправленным.
6. **Приоритет sample cache/checkpoint не перенесён.** Для существующей идентичности сначала читается готовый кэш, затем checkpoint; pending без ID сохраняет приоритет над новой проверкой формата ключа. Новая проверка применяется при переходе к запросу, а ошибка `configuration` не попадает в очистку checkpoint по `order_failed`. Алгоритм идентичности кэша и его привязка к ключу не менялись. Атомарный снимок всех настроек на всю операцию этим пакетом не вводится.
7. **Импорты и типы согласованы по исходникам.** Новый чистый helper экспортирует строковую константу и `(key: string) => boolean`, импортируется с существующей схемой `.js` из двух TS-модулей и входит в `src` конфигурации проекта. `requireApiKey` возвращает `Promise<string>`, проверяя отсутствие значения перед возвратом. Зависимостей, изменений IPC, endpoint, маршрута, account/provider settings и сетевой политики в diff нет.
