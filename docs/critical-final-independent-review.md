## Замечания

### R1 — P1, закрыто в d3fc689: после Stop допускался новый платный fallback

Основные строки: `apps/desktop/src/mock-generation-pipeline.ts:770–780`, `1828–1844`. Связанные вызовы: `anymodel-client.ts:1951–1965`, `2485`, цикл fallback изображений в `mock-generation-pipeline.ts:1424–1488`.

`finishStop` оставляет живым signal у уже отправленного paid-create без receipt, чтобы принять его результат. Это правильно для исходного запроса. Но после определённого отказа исходного создания lifecycle очищает pending, а новое создание через тот же task всё ещё разрешено: `updateSubmission` принимает статус `paused` и не учитывает `stopping`.

Сценарий:

1. Задача изображения AnyModel уже сохранила pending и отправила POST.
2. Пользователь нажимает Stop. Задача становится paused; контроллер не abort-ится, поскольку pending ещё не имеет receipt. Stop ждёт исполнения.
3. Первый POST возвращает определённый отказ, например 429 с недоступностью модели. `onRejected` удаляет pending, но не останавливает контроллер.
4. `generateImage` выбирает следующую модель либо pipeline переходит к Flow. Новый `beforeSubmit` проходит, сохраняет checkpoint и отправляет второй платный POST уже после Stop.

Та же граница относится к разрешённой ротации Flow после определённого отказа. Запрет `tick` не предотвращает внутренние fallback уже работающей задачи.

Минимальное исправление: запретить создание любого нового non-empty checkpoint при наличии `stopping` для проекта; после безопасной очистки отклонённой отправки остановить дальнейший fallback. При этом разрешить получение/сохранение receipt и завершение уже отправленного синхронного ответа. Stop, начавшийся во время записи первого checkpoint до фактической отправки, также должен завершаться без новой отправки и без ложной неизвестной оплаты, если отсутствие отправки доказано.

**Статическое закрытие:** в d3fc689 `apps/desktop/src/mock-generation-pipeline.ts:1831` отклоняет non-empty checkpoint при `stopping`. После durable записи `1844–1861` повторно рассматривается Stop: ещё не отправленная попытка durable-очищается, затем контроллер отменяется и `beforeSubmit` завершается отказом. Если очистка не записалась, checkpoint возвращается в память и возникает `QueueSubmissionCheckpointError`, сохраняя консервативную защиту 03. После definite rejection с пустым checkpoint контроллер также отменяется, поэтому fallback не может продолжить отправки. Receipt callbacks не изменены; ожидание уже отправленной попытки и сохранение позднего результата остаются допустимыми.
