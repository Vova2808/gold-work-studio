## Найденные и исправленные замечания

### R1 — P1: закрытие может потерять правку, сделанную во время повторного backup

Файл: `apps/renderer/src/App.tsx:774–790`; разрешённое закрытие выполняется в `apps/desktop/src/main.ts:1176–1183`.

`canLeaveActiveEditor()` проверяет guards редакторов, затем выполняет дополнительные асинхронные `getProject`/`updateProject` для `savesNeedingConfirmationRef`, после чего без повторной проверки разрешает закрытие. Во время этого последнего этапа дочерние редакторы не находятся в состоянии `saving`, а `navigationInFlightRef` блокирует только другой переход, не ввод.

Конкретный сценарий:

1. Запись реестра прошла, запись резервной копии не прошла. `saveProject` запомнил ID в `savesNeedingConfirmationRef` и загрузил свежий проект. После объединения черновик совпадает с реестром.
2. Пользователь закрывает окно. Guard проекта отвечает `true`, поскольку несохранённых изменений сейчас нет.
3. Повторная запись backup в цикле `canLeaveActiveEditor` занимает время. Пользователь вводит новое название или меняет другую настройку; редактор остаётся доступным для ввода.
4. Повтор backup завершается. Метод возвращает `true`; main закрывает окно. Новая правка не входила в payload и не проверялась после ожидания.

Аналогичное окно существует между завершённым `timelineGuard` и асинхронным guard основного редактора: уже сохранённый timeline снова доступен для редактирования, пока общий запрос закрытия ещё ожидает другой guard.

Минимальное исправление: не принимать пользовательские изменения на протяжении всей транзакции ухода/закрытия, включая все guards и повтор backup, либо сравнить версии черновиков после последнего `await` и отказать в уходе при новом изменении. Проверка только внутри отдельного `save()` не покрывает этот интервал.

**Закрыто в `d84b79a`.** `editingSurfaceRef` указывает на весь `desktop-frame`, включая основной редактор и timeline overlay. `inert` устанавливается синхронно до первого guard и снимается только в `finally` после всех guards/backup или ошибки. Таким образом, описанный новый пользовательский ввод в промежутке ожидания блокируется. DOM-сигнатуры `ref`/`setAttribute`/`removeAttribute` совместимы по чтению; реальное поведение фокуса и закрытия требует ручной проверки Electron.

### R2 — P2: сохранение после операции, вернувшей обновлённый проект, использует старую ревизию

Изменённая точка: `apps/renderer/src/App.tsx:578–579`. Пропущенные callers: `App.tsx:2063–2065`, `3262`, `3285`, `5804`.

`saveProject` подставляет отсутствующий `expectedUpdatedAt` из `projects` своего рендера. Но несколько асинхронных handlers сначала вызывают backend-операцию, изменяющую проект, а затем вызывают прежнее замыкание `onSave` без ревизии результата. Даже если polling уже перерисовал родителя, продолжающийся handler использует старую функцию. Проверка в `ProjectService.update` закономерно отклоняет follow-up сохранение.

Воспроизводимые по коду пути:

- Первая калибровка голоса для готового сценария: `calibrateProjectVoice` получает `result.project`, backend перед этим записывает `voice.calibration` (`main.ts:645–680`), затем UI пытается сохранить `durationMinutes` без `expectedUpdatedAt: calibratedProject.updatedAt`. Вторая запись отклоняется, измеренная длительность не применяется, sample не возвращается в плеер, UI сообщает об ошибке измерения, хотя калибровка уже записана.
- Применение нового материала из `StockMediaModal` или `DocumentaryMaterialModal`: сервис уже возвращает изменённый `Project`, затем callbacks на строках 3262/5804 повторно отправляют его сцены с ревизией до операции. Материал уже применён на backend, но модалка получает ошибку; в timeline не выполняется последующая запись Undo/обновление локального состояния.
- `DocumentaryAutoSelection` вызывает `onSelected(result.project)` после завершения изменяющего проекта автоподбора. Пустой `onSave(updated.id, {})` на строке 3285 также использует прежнюю ревизию и сообщает об ошибке успешной операции.

Минимальное исправление: передавать ревизию возвращённого проекта в каждом таком follow-up payload, как уже сделано для hero callbacks в этом diff. Для чистого обновления отображения лучше принять возвращённый проект без повторной записи. Нельзя решать проблему автоматическим чтением последней ревизии перед повторной отправкой старого payload: это уберёт смысл CAS.

**Закрыто в `d84b79a`.** Все четыре указанных callers теперь явно передают `expectedUpdatedAt` из `calibratedProject`/`updated`. Пустое сохранение автоподбора оставлено, но получает ревизию возвращённого результата. При реальном последующем изменении проекта CAS по-прежнему отклонит устаревший payload.

## Статически рассмотренные контракты

Просмотрен объединённый actual diff всех 14 изменённых файлов. Для проверки связей прочитаны необходимые участки `FileProjectRepository`, `fs-utils`, Flow/Lumean клиентов, `project-editor-merge`, `scenario-draft-merge`, material callbacks и существующего startup. Документы `queue-recovery-03.md` и `project-preservation-05.md` использованы как описание намерений, а не доказательство корректности.

- **Очередь и повреждённый JSON.** Новый reader проверяет структуру/ID/тип receipt, не переименовывает и не затирает повреждённый файл, запоминает отказ до перезапуска. `replace` перечитывает исходный файл и использует существующую durable-запись без copy fallback. `pipeline.initialize` вызывается до подключения IPC и таймера выполнения, поэтому ошибка загрузки не превращается в пустую рабочую очередь.
- **Платная отправка.** AnyModel/Google медиа получают callbacks перед POST. Новая отправка требует успешного сохранения pending; транспорт не делает автоматические повторные POST при наличии lifecycle и запрещает redirect. При определённом отказе создания pending снимается; неясный сетевой результат остаётся заблокированным. Установление proxy-туннеля различается с ошибкой после HTTP-отправки существующим типом `ProxyConnectError`.
- **ID и сбои записи.** AnyModel video и классический Veo сохраняют receipt до polling; retry выбирает провайдера из receipt. Flow использует сохранённый account/job, Lumean — order ID и проверку отпечатка текста/шаблона. При ошибке сохранения полученный ID остаётся в памяти, а предыдущий pending на диске не позволяет повторить оплату после аварии. До новой отправки сбой записи pending возвращает предыдущее состояние в памяти.
- **Завершение и restart.** Запуск task сохраняется до `beginExecution`; при сбое этого сохранения новые исполнения не стартуют. Завершение платной операции защищено от оставления в памяти безусловного `done` при последующей ошибке фиксации. Старые начатые медиа-задачи без пригодного receipt/pending и без tracking v2 блокируются консервативно, без вывода о старом провайдере из текущих настроек.
- **Очистка и перезапуск.** `clearAll`, `clearFinished`, start/regenerate/assemble учитывают незавершённые receipts/unknown submissions; общая озвучка учитывает все narration scene IDs. Известный заказ у остановленной задачи можно возобновлять через предусмотренный UI, без создания нового заказа.
- **Сохранение проекта.** `expectedUpdatedAt` проверяется внутри сериализованной мутации реестра и не входит в сохранённый input. Новая ревизия возрастает минимум на 1 мс. Обработчик metadata-save ожидает backup; ошибка backup явно отличается от ошибки реестра. `LocalProjectStorage` читает полный актуальный проект внутри последовательного writer и повторяет snapshot, если версия успела измениться.
- **UI и close.** Основные редакторы передают ревизию своего черновика, сохраняют правки при ошибке и объединяют входящие сцены/настройки существующими функциями merge. Более старые project responses не заменяют более свежий родительский snapshot. Native close ожидает renderer, таймаут сам не разрешает закрытие; ошибка guard оставляет окно открытым. Исправления R1/R2 дополнительно просмотрены, как описано выше.
- **Типы по чтению.** Просмотрены `ProviderVideoJob`, discriminators receipt, `PaidMediaSubmission`, новые параметры клиентов, optional `DesktopApi.onWindowCloseRequested`, preload и props редакторов. Явной новой ошибки сигнатуры в этих изменённых связях не найдено. Это не typecheck; старые typed fixtures и тестовые файлы не изменялись и не запускались.
- **Lumean L1.** Diff не меняет parser/пагинацию/папки `/templates`, hook загрузки или сохранение UUID, добавленные в L1. Связанный путь калибровки затрагивает R2. Платный TTS использует существующий order lifecycle; новое расширение receipts не заменяет его AnyModel/Google-маршрутом.
